SecureVote Threat Model

SecureVote is a portfolio security prototype. This page summarizes what the project is designed to demonstrate, what it does not claim, and where the review evidence lives in the repository.

Assets and Trust Boundaries
  • Voter identity and enrolment stay in authenticated flows; driver licence, electoral-roll name, address, suburb, state, and postcode fields are encrypted at rest.
  • Ballot authorization is separated from anonymous ballot submission through blind signatures.
  • Manager results, audit logs, and election administration are role-gated.
  • Vault transit signing is the preferred production-style result-signing boundary when configured.
  • MySQL, Vault, and Flask run behind nginx and ModSecurity in the Docker architecture.
In-Scope Threats
  • Double voting and race conditions during vote authorization.
  • Linking authenticated voter identity to anonymous ballot content.
  • Credential guessing, reset abuse, weak passwords, and automated login attempts.
  • PII disclosure from database access or over-broad manager workflows.
  • Audit log tampering and unsigned result publication.
  • Unsafe production deployment with local demo controls enabled.
Implemented Controls
  • RSA blind signatures, browser-side unblinding, and a cookie-free anonymous ballot endpoint.
  • Election-scoped candidates, ballots, one-time identity-separated authorizations, identity-free spent nullifiers, and immutable rosters after opening.
  • Locked voter and enrolment revalidation, one blind authorization per voter and election, identity-free spent-nullifier replay prevention, and database uniqueness constraints.
  • Immutable signed results with durable backend, algorithm, key identifier, and Vault key-version provenance.
  • Versioned ChaCha20-Poly1305 envelopes protect driver licence, electoral-roll name, address, suburb, state, and postcode fields and fail closed on malformed, tampered, or wrong-key values, with HMAC blind indexes for driver licence lookup.
  • Password policy, email OTP MFA, account lockout, anti-bot login nonce, honeypot, and Origin checks.
  • HMAC-chained JSONL audit logs plus manager-visible chain verification.
  • Environment detection that blocks developer controls and test seeding in production-like settings.
Residual Risks and Non-Claims
  • This is not a certified, audited, or production election service.
  • No public internet election should rely on this prototype without independent security review.
  • Endpoint behavior, availability, coercion resistance, client compromise, and operational monitoring need more evidence.
  • Local RSA signing is a development mode only. If Vault is selected but unavailable, result signing fails closed.
  • The prototype supports one region and one contest per election; blind authorization loss is unrecoverable without a governed recovery protocol.
  • Identity-free storage does not remove network metadata or small-anonymity-set timing correlation.
  • Email, electoral-roll date of birth, user licence state, enrolment status, and operational metadata remain plaintext in the database and require strict access control and data minimization.
  • Audit chains and signed results improve tamper evidence but do not replace independent election governance.
